## The three biggest code findings

### 1. BookaRide loses a paid booking if the Stripe key breaks — finding #17, critical

`api/webhook/stripe.js:37` answers **HTTP 200** when `STRIPE_SECRET_KEY` is
missing or malformed, after logging *"CRITICAL … payment NOT processed"*. Stripe
treats any 2xx as delivered and **drops the event permanently**. The customer has
already paid at that point, so: money taken, booking never marked paid, no
confirmation email, no calendar event, no retry, ever.

The file already knows the right pattern — six lines below, a missing
`STRIPE_WEBHOOK_SECRET` returns 500 "rejecting webhook to prevent payment
forgery". The missing-key branch is inconsistent with its own neighbour.

I checked the obvious mitigation and it does **not** save it:
`api/bookings/sync-pending-payments.js` can reconcile pending bookings against
Stripe, but it is behind `verifyAdmin` (a human must POST it), it is **not in
`vercel.json`'s crons** (only the SEO agent is), and it reads the *same*
`STRIPE_SECRET_KEY` — so it fails on the identical root cause.

**Fix:** return 5xx like its neighbour, so Stripe retries with backoff and the
event survives until the key is fixed. Keep the CRITICAL log, and alert — a
config error on the money path should page someone, not answer OK.

### 2. Gluecron auto-merges unreviewed PRs once a customer's AI budget runs out — finding #32, high

Verified against `origin/main`, not the stale local checkout.
`auto-merge.ts`'s `aiCommentLooksApproved()` is a **deny-list that returns true by
default** — it rejects only bodies containing `ai review unavailable`,
`severity: blocking`, or matching `/flagged \d+ item/`. The comment Gluecron posts
when a customer's monthly AI budget is exhausted is:

> `<!-- gluecron-ai-review:summary -->` … **AI review skipped** — Your monthly AI
> token budget has been reached.

It carries the marker, so `aiApprovedForPr()` treats it as *the* AI review, and it
matches none of the three rejections. *"AI review skipped"* is not *"AI review
unavailable"*. So the budget running out satisfies the AI-approval gate and every
PR in that repo becomes auto-mergeable with no AI review at all.

The error path **was** considered (`ai-review.ts:411` writes "AI review
unavailable", correctly rejected). The budget path was simply missed. Two further
findings in the same file point the same way — Gluecron's merge gates fail
**open**, including one where a swallowed DB error turns "required checks have not
passed" into "all gates green".

**Fix is a product decision, which is why it's yours:** should an unreviewed PR
block auto-merge, or merge with a visible warning? Blocking is safer and will
annoy customers who have hit their budget.

### The spine could not read AlecRae's commit — and what that nearly cost

The 23:04 sweep took AlecRae with the data-integrity lens and logged *"NOT a git
checkout, no commit recorded"*. It is very much a git checkout; I had run `git log`
in it by hand hours earlier.

The difference is `HOME`. `/opt/alecrae` is owned by `alecrae:alecrae` and the
service runs as root, so git refuses it for "dubious ownership" unless an exception
is configured. Root's `~/.gitconfig` **has** that exception — which is exactly why
it works interactively and why nobody noticed — but `jarvis-code-health.service`
sets no `User=` and no `Environment=HOME`, so systemd gives the process no HOME and
git never reads that file. `spawn-agent.js` sets `HOME=/root` explicitly for its
claude spawns, which is why the review agents ran perfectly while this one call did
not. Fixed by passing `-c safe.directory=<cwd>` rather than editing anyone's
gitconfig, and proven under a bare `env -i`.

**Every AlecRae finding in the table — all fourteen — carries a NULL commit_sha**
because of it. That is the safeguard CLAUDE.md describes for exactly this platform,
and it has never once run.

## This box's DNS intermittently denies that vapron.ai exists

Found by chasing a false "critical" in the first audit sprint after tonight's
repairs, and it is an infrastructure fault rather than a code one — so it is
reported, not fixed. `/etc/resolv.conf` is shared with AlecRae, Gluecron and the
Coolify stack, and reordering nameservers on a co-tenant box unattended is not
something I will do.

The measurement, from the box:

```
system resolver, vapron.ai        ENOTFOUND on 5 of 8, then 2 of 6, then 4 of 8
system resolver, 8 other domains  6/6 every time
1.1.1.1, vapron.ai                resolves every time → 149.28.119.158 (box 158)
```

`/etc/resolv.conf` lists `108.61.10.10` (Vultr) first, then `9.9.9.9`. **glibc
treats an NXDOMAIN as authoritative and does not fall through to the next
`nameserver` line** — so when the first resolver wrongly says "no such name", that
is the whole answer, and the second server is never asked.

What it has been costing you:

- The audit scored vapron **critical / 50** tonight on `fetch failed`, while its
  own Chromium screenshot of that exact URL succeeded in the same second and
  produced a 298KB PNG. That verdict was written to `platform_state`, so the deck
  showed a healthy platform as critical.
- self-heal has been repeatedly seeing vapron "DOWN", waiting out the debounce and
  then clearing it — the log says *"memory says error but LIVE probe returned 200
  — false alarm"* at 02:48 today. The guardrails held, but that churn is this.
- It very likely explains the **13% probe-failure rate on vapron.ai** recorded in
  `fleet-check.sh`'s own comment, which was attributed to a slow site.

I have made Jarvis resilient to it (self-heal now takes a second opinion before
ever telling you a domain has vanished — proven live, 8/8 correct on both the
flaky domain and the genuinely expired one). But the box still has a resolver that
lies, and everything on it inherits that.

**Suggested fix, yours to make:** put a reliable resolver first —
`nameserver 1.1.1.1` ahead of `108.61.10.10` — or run `systemd-resolved` so a
bogus NXDOMAIN from one server is retried against another. Check first whether
`resolv.conf` is being rewritten by cloud-init or DHCP, or the change will not
survive a reboot.
