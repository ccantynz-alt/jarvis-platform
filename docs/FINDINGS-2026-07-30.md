## Read these three first

### 1. BookaRide loses a paid booking if the Stripe key breaks — finding #17, critical

`api/webhook/stripe.js:37` answers **HTTP 200** when `STRIPE_SECRET_KEY` is
missing or malformed, after logging *"CRITICAL … payment NOT processed"*. Stripe
treats any 2xx as delivered and **drops the event permanently**. The customer has
already paid at that point, so: money taken, booking never marked paid, no
confirmation email, no calendar event, no retry, ever.

The file already knows the right pattern — six lines below, a missing
`STRIPE_WEBHOOK_SECRET` returns 500 "rejecting webhook to prevent payment
forgery". The missing-key branch is inconsistent with its own neighbour.

I checked the obvious mitigation and it does **not** save it:
`api/bookings/sync-pending-payments.js` can reconcile pending bookings against
Stripe, but it is behind `verifyAdmin` (a human must POST it), it is **not in
`vercel.json`'s crons** (only the SEO agent is), and it reads the *same*
`STRIPE_SECRET_KEY` — so it fails on the identical root cause.

**Fix:** return 5xx like its neighbour, so Stripe retries with backoff and the
event survives until the key is fixed. Keep the CRITICAL log, and alert — a
config error on the money path should page someone, not answer OK.

### 2. Gluecron auto-merges unreviewed PRs once a customer's AI budget runs out — finding #32, high

Verified against `origin/main`, not the stale local checkout.
`auto-merge.ts`'s `aiCommentLooksApproved()` is a **deny-list that returns true by
default** — it rejects only bodies containing `ai review unavailable`,
`severity: blocking`, or matching `/flagged \d+ item/`. The comment Gluecron posts
when a customer's monthly AI budget is exhausted is:

> `<!-- gluecron-ai-review:summary -->` … **AI review skipped** — Your monthly AI
> token budget has been reached.

It carries the marker, so `aiApprovedForPr()` treats it as *the* AI review, and it
matches none of the three rejections. *"AI review skipped"* is not *"AI review
unavailable"*. So the budget running out satisfies the AI-approval gate and every
PR in that repo becomes auto-mergeable with no AI review at all.

The error path **was** considered (`ai-review.ts:411` writes "AI review
unavailable", correctly rejected). The budget path was simply missed. Two further
findings in the same file point the same way — Gluecron's merge gates fail
**open**, including one where a swallowed DB error turns "required checks have not
passed" into "all gates green".

**Fix is a product decision, which is why it's yours:** should an unreviewed PR
block auto-merge, or merge with a visible warning? Blocking is safer and will
annoy customers who have hit their budget.

### 3. universal-ai-operator destroys files and reports success — and has no version control

This is the one I'd look at tonight. `/root/universal-ai-operator` is a CrewAI
agent whose tools write into **`target_code/zoobicon`** — and the operator
directory itself has **no `.git` at all**. Not "no remote": no history, no
revert, no bisect. Four confirmed findings, all in the write path:

| Finding | What it does |
|---|---|
| `master_engine.py:36` (high, data-loss) | `write_project_file` opens with mode `'w'` — immediate truncate — then returns `"Successfully updated"` unconditionally. No size, completeness, or atomic temp-and-rename guard. A partial payload silently destroys the file. |
| `jarvis_setup_wizard.py:28` (high, data-loss) | Overwrites the live, git-untracked `jarvis_slack.py` with generated code that **does not compile** — the verifier rendered the f-string through `ast` and got `SyntaxError: invalid syntax` on `def handle_mention(body, say)::` — then prints SUCCESS. |
| `master_engine.py:18` (high, correctness) | `deploy_verified_code` reports **"DEPLOYMENT SUCCESSFUL"** when the commit failed. It runs `git commit` without `check=True` and its only failure test is `if "nothing to commit" in stdout`, so a missing `user.email`, a rejecting hook or unmerged paths all read as success. |
| `agent_runner.py:600` (medium, data-loss) | `_read_active_work_manifest` collapses every non-200 (including 5xx/403) into an empty manifest, and `claim_work` then PUTs it back — **erasing every other agent's claims**. `release_work` has a guard for exactly this; `claim_work` doesn't. |

Truncating writes plus false success reports plus no version control is the
combination that loses work permanently. **Suggested order:** `git init` the
operator directory, then make `write_project_file` atomic (temp file + rename)
before running it against Zoobicon again.

## Everything else, by platform

**AlecRae** — 3 confirmed, all re-verified against `origin/main` (the local
checkout was 28 commits / 10 days behind, so this mattered):

- **critical** — inbound SMTP answers `STARTTLS` with 220 and marks the session
  secure **without upgrading the socket**, and nothing in the tree upgrades it
  (`net.createServer` confirms it is a live listener). Two consequences: a
  TLS-requiring sender cannot deliver at all, and any client can send `STARTTLS`
  then continue in **plaintext** while the `requireTls` gate believes the session
  is encrypted.
- **high** — the MTA re-delivers on retry. `activeRecipients` is filtered only
  against the suppression list, never against `deliveryResults.status === 'sent'`,
  so any BullMQ retry emails everyone who already received it. Affects the relay
  path as well as the direct-MX path originally reported.
- **high** — the DLQ retry marker is keyed on the job being processed, but the
  retry is enqueued with a *new* id, so `markPermanentlyFailed` is unreachable for
  retries: a permanently-failing job re-queues hourly forever, with the id and the
  store growing each time.

**GateTest** — 3 confirmed high, all in its own *fix* pipeline reporting false
success (files that failed to commit counted as fixed; the test gate running
against unmodified source; an API key emailed on every Stripe retry while the DB
keeps the original). Note Jarvis only ever invokes `--suite web` and `--list`, so
**deploy gating is not compromised by these** — but anyone relying on GateTest's
auto-fix is being told work landed when it didn't.

**Gluecron** — besides #2 above: one **critical** claim of a blind
`git update-ref` force-move of a base branch that I could **not confirm** at
`origin/main` (both `updateRef` callers I traced pass a compare-and-swap parent,
and that checkout is 13 commits behind). It is annotated as needing
`lib/pr-merge.ts` checked before anyone acts on it — a base-branch force-move
would discard commits, so it deserves a real answer either way.

**BookaRide** — besides #1: a contact form that answers *"Message sent
successfully"* when the DB insert **and** both emails failed (confirmed), a
return-leg calendar event recorded as a clean sync when it failed (confirmed),
plus reference-number reissue, non-atomic payment confirmation, and a reminder job
that re-emails customers.

**Voxlen** — swept last, and the pick of the day for a dictation app, because all
four confirmed findings are ways it keeps *reporting success while producing
nothing*:

- **high** — if the audio input stream fails to build, the only handling is a
  `log::error!` inside the capture thread: `status` has already been set to
  `Listening` and `Ok` returned. The watchdog's sole trigger is
  `take_device_fault()`, which stays false, so it loops forever without
  restarting capture. Nothing downstream rescues it either — the Deepgram session
  is kept alive by KeepAlive frames, so it never times out into
  `streaming-disconnected`, and the frontend only listens for `audio-recovery-*`
  events that this path never emits. **Craig sees "Listening" with a dead mic,
  indefinitely.**
- **high** — `save_session` failure is swallowed by an empty catch labelled
  *"Non-Tauri environment — skip"*, while the UI toasts *"Session saved"*
  unconditionally, outside the persistence branch entirely. It matters because
  HistoryPanel is fed solely by `get_history` — the Rust key that failed to
  write — so the session is genuinely gone from the panel, and the same empty
  catch appears twice (autosave and DictationPanel).
- **medium** — a Deepgram auth failure re-enters the connect loop with no backoff
  and no failure counter. The arm's own comment says *"Fall through to reconnect
  logic below"*, but Rust match arms do not fall through, so it skips the
  `consecutive_failures` increment, the cap, and the sleep — the exact "endless
  reconnect storm" the counter was written to prevent.
- **medium** — `clipboard_paste` reports success even when the paste keystroke
  never lands (Windows `SendInput` and Linux `xdotool` results are both
  discarded, while the neighbouring `simulate_keyboard` and the macOS path *do*
  check), then a 600 ms timer clears the clipboard. That false `Ok` also defeats
  the designed recovery in DictationPanel, which would have copied the text to
  the clipboard and said so. The verifier downgraded this from high after
  establishing the dictated text is not always destroyed.

Three more are filed unverified below the verification threshold: an unparseable
history file silently becoming an empty session list that the next save then
persists over everything, `clear_clipboard` ignoring PowerShell's exit status
while reporting the clipboard cleared, and model downloads with only a connect

## Jarvis itself

**38 findings against Jarvis are filed and fixed**, plus a run of defects found
by hand this morning before the spine existed — 53 commits on 2026-07-30, every
fix carrying a named artifact rather than an argument. The two checkable numbers:
`git log --since=2026-07-30` and
`curl -s 'http://127.0.0.1:9200/memory/findings?platform=jarvis&limit=60'`. Both
move while the loop runs.

The recurring shape is worth naming: almost none of them threw an error. They were
systems that had *silently stopped protecting the fleet* —

- a daily repair cap that could never reset, so one bad day disabled a platform's
  auto-repair permanently (four platforms were carrying counts from mid-July);
- jobs stuck `running` forever after a lost status write, which made self-heal and
  the audit runner refuse to touch that platform;
- a status row that erased its own health score on every job completion;
- an audit that could overwrite a real outage with "healthy";
- a digest that discarded up to 200 notifications when a send failed;
- a verifier losing 3 of 4 verdicts to a greedy regex;
- the confirmation gate, twice — first too narrow to accept "please", then loose
  enough to accept "i need to run";
- **no self-monitoring at all** — no `OnFailure=` on any unit, nothing checking
  unit state, and the HUD watching four ports of twelve. Demonstrated live when a
  bad deploy of mine crash-looped `jarvis-slack` for a minute and the inbox
  recorded nothing;
- **anyone in the Slack workspace could launch a root agent** — no sender check
  existed at all, and Slack's dispatch path has no confirmation turn. Only
  unexploitable by accident, because every message had been throwing since
  2026-07-08; fixing that crash the same morning made it live;
- **`Cookie: a=%` killed the deck** — `decodeURIComponent` throws, the WS upgrade
  handler is raw Node, and the parse ran *before* the token check;
- two that cost money: the ElevenLabs budget under-counted by up to 95% under
  concurrency, while every connected device was separately charged for the same
  sentence;
- **every "a failed notification is retried, not lost" guarantee was vacuous** —
  they all rest on the transport throwing, and `sendSlack` never throws. Slack
  answers **HTTP 200** with `{"ok":false,"error":"ratelimited"}`, so a refused
  message was indistinguishable from a delivered one: a critical alert Slack
  rejected was reported as sent, dropped entirely, and then suppressed by its own
  dedupe key for the next 30 minutes. The louder the incident, the more thoroughly
  it was buried;
- **a voice turn could go silent without anything failing** — the ElevenLabs
  socket had no handshake or first-audio timeout, so a slow (not dead) ElevenLabs
  produced no `open`, no `error` and no `close`. Every sentence went into the
  stream, the turn recorded itself as spoken, and the reply arrived on screen with
  the client waiting for audio that was never coming. `spokenAny` meant "text was
  handed over"; it now judges on audio actually returned;
- **the daily audit was inventing scores for two platforms** — `ZOOBICON_PATH` and
  `ALECRAE_PATH` pointed into `/var/www`, which does not exist on this box. The
  dead path went to `spawnSync` as cwd, the `ENOECT`-style error text matched none
  of the error patterns so `errors: []`, the arithmetic landed on a tidy
  `100-20-10 = 70` → `warning`, and the notifier only speaks for `critical`. Your
  flagship and AlecRae were "audited" every day for weeks and the number was made
  up. AlecRae's first genuine audit, run today: **healthy, 100/100, 36/36 turbo
  tasks passing**;
- and **the repo's `systemd/` folder was not the deployed config** — eleven
  drop-in files on the box overrode `MemoryMax` on ten services, so reading a unit
  told you a limit that had not applied since 17 July.

what the HUD should say, not a cleanup, and it wants doing with the HUD in front
